Mint New Bond

How it works

Minting calls the Mint choice on the SimpleTokenRules factory. Its controller is admin, owner — both must authorize the transaction, so both must be on the same Canton participant. The result is a SimpleHolding contract with signatory admin, owner, ensuring both parties can see and interact with it.

Holdings

How it works

Holdings are SimpleHolding contracts (active bonds) or LockedSimpleHolding contracts (pending transfers). Their signatories — admin, owner for SimpleHolding; admin, owner, lock.holders for LockedSimpleHolding — determine which parties and participants can see them. Locked holdings have an expiry-based lock set during the transfer process.

Transfer Bond

How it works

Transfers exercise the TransferFactory_Transfer choice on the SimpleTokenRules factory via the TransferFactory interface. The controller is transfer.sender only — no admin authorization needed. The factory was made visible on all participants by adding every party as an observer at creation time, enabling cross-participant transfers. The result is a LockedSimpleHolding and a SimpleTransferInstruction pending the receiver's action.

Pending Transfers

How it works

When a transfer is initiated, a SimpleTransferInstruction is created with signatory admin, sender and observer receiver. The receiver can Accept (creates a new SimpleHolding for them) or Reject (returns funds to sender). The sender can Withdraw. During the pending period, funds are locked in a LockedSimpleHolding visible to the receiver as an extra observer.

Burn Bond

How it works

SimpleHolding has two burn choices: Burn (controller owner) and BurnByAdmin (controller admin). Both call archive self, and since the holding's signatories are admin, owner, Daml requires both parties to authorize the archival — that's why both IDs are included in the submission. The "Burn as Admin" checkbox uses BurnByAdmin but still needs the owner's authorization.

Parties

How it works

A Canton participant is a node that hosts parties. Each party lives on exactly one participant. Allocating a party creates its identity on the ledger. The party hint (e.g. "bob") is just a suggestion — the full identifier includes a cryptographic hash (bob::1220...). The backend resolves short names to full IDs when submitting Daml commands.
